# 브라우저만 사용하는 관리자·학생 통합 E2E

**“관리자·학생 통합 E2E 34단계를 검증해줘”**라고 요청하면 관리자 준비부터 학생 제출과 관리자 검토까지 한 흐름으로 실행한다. 관리자 계정만 미리 준비하면 학생 계정과 수강 등록, 팀 구성, 마일스톤은 모두 화면에서 만든다. 실행마다 새 강좌·분반을 사용한다.

Playwright의 `page.goto`, 클릭, 입력, 파일 선택과 화면 assertion으로만 진행한다. HTTP 클라이언트, `page.request`, `fetch`, API seed/cleanup, 응답 모킹, 인증 상태 주입은 사용하지 않는다. 테스트에서 XLSX/PDF/PNG 파일을 메모리에 만드는 것은 업로드할 파일 준비이며 서버 데이터 생성은 UI가 담당한다. 실패 분석용 네트워크 기록은 화면이 보낸 요청의 메서드·경로·상태 코드만 수집한다.

## 준비와 실행

저장소 루트 `.agent-local/e2e/integrated.env`에 아래 값을 설정한다. 파일 경로는 `OOP_E2E_INTEGRATED_ENV_FILE`로 바꿀 수 있고 같은 이름의 환경변수를 직접 설정해도 된다.

```dotenv
OOP_E2E_ADMIN_NUMBER=<관리자 학번>
OOP_E2E_ADMIN_PASSWORD=<관리자 비밀번호>
OOP_E2E_API_URL=https://api.example.test
# 이미 배포된 프런트엔드를 검사하려면 아래 값을 설정한다.
# OOP_E2E_BASE_URL=https://frontend.example.test
```

`OOP_E2E_BASE_URL`이 없으면 현재 브랜치의 Vite를 localhost:5173에 시작하고 API 프록시를 연결한다. 이미 실행 중인 서버를 자동으로 재사용하지 않는다. 원격 프런트엔드는 검사할 변경이 배포돼 있고 MSW가 꺼진 환경이어야 한다.

한 번은 “관리자·학생 통합 E2E 34단계를 검증해줘”, 반복 검증은 “새 데이터로 관리자·학생 통합 E2E 34단계를 두 번 연속 검증해줘”라고 요청한다. UI를 직접 보려면 “통합 E2E를 Playwright GUI로 열어줘”라고 요청한다. 아래는 에이전트 내부 실행·문제 해결용 참고다.

```sh
pnpm install
pnpm --filter @aics/oop exec playwright install chromium
pnpm test:e2e:integrated
# 새 데이터셋으로 전체 34단계를 연속 두 번 실행
pnpm --filter @aics/oop test:e2e:integrated --repeat-each=2
```

관리자는 생성 분반의 담당 교수여야 한다. 공지 쓰기는 서버가 활성 분반의 교수 소유권을 검증한다. 강좌·분반 생성, 명단 업로드, 팀 배정 확정, 마일스톤·평가 관리 권한이 있어야 한다. 실제 데이터가 만들어지므로 테스트 전용 서버를 사용한다. 계정 비밀번호가 실행 trace에 남지 않도록 trace/video는 끈다. 자동 재시도는 하지 않는다.

## 로그인 계정

실행 폴더의 `dataset.json`이 해당 실행의 실제 값이다. 이름에 들어가는 `E2E249-<실행 시각>`으로 데이터 범위를 식별한다. 역할명은 짧은 한글로 붙여 명단 가져오기의 이름 32자 제한을 지킨다.

| 역할               | 로그인 시점                    | 팀과 용도                                                  |
| ------------------ | ------------------------------ | ---------------------------------------------------------- |
| 관리자             | 처음과 각 관리자 검토 단계     | 강좌·분반·학생·팀·마일스톤 준비, 피드백과 결과 조회        |
| `survey`           | 수강 등록 뒤, 팀 배정 전에     | 설문 제출과 배정 대기 확인. 팀 명단에서는 제외             |
| `leader`           | 팀 배정 확정 뒤                | 주제 확정, 제안서·중간 점검·발표·최종보고서 제출, 상호평가 |
| `memberA`          | 주제 투표와 최종보고서 제출 뒤 | 주제 투표·현재 제출 버전 승인                              |
| `memberB`          | 주제 투표와 최종보고서 제출 뒤 | 주제 투표·현재 제출 버전 승인                              |
| `memberC`          | 주제 투표와 최종보고서 제출 뒤 | 주제 투표·현재 제출 버전 승인                              |
| `comparisonLeader` | 회의 접근 거부·발표 자료 제출  | 다른 팀 회의 접근 거부, 비교팀 주제 확정·발표 업로드       |
| `comparisonMember` | 비교팀 주제 확정 단계          | 대안 후보 등록·투표                                        |

학생 학번은 실행 시각에서 생성한 고유 문자열이며 실제 학번을 재사용하지 않는다. 학생 명단 업로드의 신규 계정 생성 계약에 따라 **연락처가 초기 비밀번호**가 된다. `dataset.json`의 `users.<역할>`에 학번·이름·이메일·연락처·초기 비밀번호가 함께 저장된다. 관리자 비밀번호는 데이터셋에 복사하지 않는다. 회의·공지 입력 날짜는 실행 시점의 서울 달력 날짜로 고정하고 브라우저 시계를 바꾸지 않는다. 계정마다 별도 브라우저 context를 사용하므로 서로의 세션을 덮어쓰지 않는다.

선행 실패 후 다음 독립 단계가 시작할 때 현재 페이지가 `/login`이면 같은 context에서 일반 로그인 화면을 한 번 사용한다. 이 복구는 `login-recoveries.json`에 기록하며, 실패한 변경 요청을 다시 보내거나 그 단계를 통과로 바꾸지 않는다.

공개일은 실행 전날, 일반 마감은 실행 7일 뒤로 잡는다. 발표 파일을 업로드한 뒤에만 관리자 화면에서 발표 제출 마감을 전날 01:00, 평가 시작을 전날 02:00, 종료를 다음 날 23:59로 변경한다. 평가 기간을 저장해야 발표 평가 탭의 순서·항목 설정이 열린다. 브라우저 시계나 API 응답을 조작하지 않는다.

## 데이터셋과 수동 재생성

실행 자료는 `.agent-local/e2e/integrated/runs/<실행 키>/`에 저장한다.

- `dataset.json`: 실행 키, 강좌·분반·팀명, 합성 계정 7개와 입력값, 날짜.
- `*-students.xlsx`: 학번/이름/이메일/연락처/역할의 7개 행. 관리자 학생 명단 업로드용.
- `*-teams.xlsx`: 팀명/학번/이름/팀장/역할의 6개 행. 관리자 팀 명단 업로드용.
- `reset-targets.json`: 생성 전 계획과 생성·수정·삭제 직후 갱신되는 회의/액션/공지 리소스 상태, UI 경로, 삭제 시도와 결과, 실패·미실행 사유, 잔여 대상과 수동 정리 순서. 결과 불명은 `unknown`으로 보존한다. 공지와 서버 알림 행은 의도적으로 남긴다. 새 글 배지의 읽음 상태는 브라우저 로컬 저장소에만 유지되며 context 종료 시 폐기되므로 서버 정리 대상이 아니다.
- `e2e-submission.pdf`: 발표·최종보고서 수동 업로드에 사용할 PDF.
- `milestones.json`: 화면 링크에서 확인한 마일스톤 경로. 서버 재생성 후에는 새 값을 사용한다.
- `network.json`: 단계·사용자 역할과 UI 요청의 메서드·경로·상태 코드. 원문 응답, 인증 헤더, 토큰은 기록하지 않는다.
- `outcomes.json`: 단계별 통과/실패/선행 실패로 인한 미실행과 사유.
- `<단계>-<역할>-route.json`: 실패 시 UI 경로. 모든 실패 경로에서 기존 마스크를 적용한 스크린샷을 저장하고, 실행 키가 있는 열린 대화상자의 증거도 유지한다. 전체 분반 화면의 본문을 덤프하지 않는다.
- `M03/M04/M08/M09-*.png`, `N01/N02/N03/N04-*.png`: 원본·수정 본문, 새 글·읽음의 성공 증거. 원시 문서 `pre`, 비밀번호, 해당 실행 외 관리자 표 행을 가린다.
- `browser-errors.json`: 단계·역할을 포함한 브라우저 JavaScript 오류.
- `console-errors.json`: 단계·역할을 포함한 console 오류. 네트워크 상태와 함께 조사한다.
- `login-recoveries.json`: 다음 독립 단계에서 수행한 일반 UI 로그인 복구.
- `evidence-errors.json`: 화면 캡처·파일 쓰기 오류. 다른 단계는 계속 실행하지만 증거 오류가 있는 실행은 성공으로 계산하지 않는다.

계정 JSON과 XLSX에는 초기 비밀번호로 사용하는 연락처가 있으므로 실행 폴더는 Git에 넣지 않는다. 수동 재현을 함께할 서버 담당자에게는 필요한 실행 폴더를 별도로 전달한다.

**매번 처음부터 실행할 때:** “새 데이터로 통합 E2E를 다시 검증해줘”라고 요청하면 새 학번·새 강좌·새 분반·새 팀을 만든다. 이전 제출 데이터를 삭제하거나 되돌릴 필요가 없다. 회의록은 M10에서 UI로 삭제하고 M11/M12에서 액션 연쇄 삭제와 관리자 missing 상태를 확인한다. 그 전에 실패해 소유 경로가 남으면 단 한 번의 제한된 UI 정리를 시도한다. 이미 결과가 불명확한 삭제는 반복하지 않는다. 공지·알림과 기본 계정/강좌/제출 데이터는 서버에 남는다.

**같은 데이터셋을 수동 재생성할 때:** 서버 담당자가 먼저 해당 실행 키에 속한 데이터만 초기화했는지 확인한 뒤 학생·팀 XLSX를 위 순서대로 다시 업로드한다. 제출 버전·파일 연결·확인 기록·문서 영역 완료·수정 요청·평가 응답까지 정리해야 같은 초기 상태가 된다. 팀장 확정과 프로젝트 생성도 다시 진행한다. 마일스톤/팀/프로젝트/제출물 ID는 새 값이 생기므로 예전 숫자 ID를 재사용하지 않는다. `dataset.json`의 날짜가 지났다면 현재 기준으로 다시 잡는다.

브라우저에는 제출 완료·설문·평가 전체를 원상복구하는 통합 기능이 없다. 따라서 자동화는 초기화용 비공개 API를 호출하지 않는다. 기존 서버 ID를 보존해야 하는 초기화는 [기존 초기화 가이드](./reset-and-seed.md)의 범위와 의존성 순서를 서버 담당자와 함께 적용한다. 단순 탈퇴·재활성화나 팀원 승인 취소만으로 제출 이력이 초기화되지는 않는다.

## 결과 해석

HTML 보고서는 `.agent-local/playwright/integrated-report/index.html`에 생긴다. 한 테스트의 34단계를 worker 1개, retry 0회로 실행한다. 전체 한도는 1,200초이며 회의/공지 단계는 각각 90초, 기존 단계는 180초 안에서 종료한다. 파일·화면 증거 실패도 형제 단계의 실행을 막지 않는다. 모든 단계 결과는 매 단계와 종료 시 저장하고 브라우저 context는 최종 저장 실패 시에도 닫는다.

실행 순서는 01–06 → M01–M12 → N01–N04 → 07–18이며 의존성은 `integrated/stages.ts`에 명시한다.

| 단계                        | 선행 단계              |
| --------------------------- | ---------------------- |
| 01                          | 없음                   |
| 02 / 05 / N01               | 01                     |
| 03 / 04                     | 02                     |
| 06 / M01 / 17               | 04                     |
| 07 / 09 / 11 / 14           | 05, 06                 |
| 08 / 10 / 12 / 13           | 각각 07 / 09 / 11 / 12 |
| 15 / 16                     | 14                     |
| 18                          | 17, 06                 |
| M02 / M04 / M05 / M07 / M10 | M01                    |
| M03 / M06                   | M02                    |
| M08                         | M07, M02               |
| M09                         | M07                    |
| M11                         | M10, M02               |
| M12                         | M10                    |
| N02                         | N01, 02                |
| N03                         | N01                    |
| N04                         | N03, 02                |

02 실패에도 N01/N03은 실행하고 학생 읽기 N02/N04만 차단한다. 05/06 실패는 회의·공지를 막지 않으며 M/N 실패는 제출·검토를 막지 않는다. 실패 또는 미실행은 통과에 포함하지 않고 전체 실행은 실패로 종료한다. 실제 선행 조건으로 차단된 단계에는 사유를 기록한다. 빈 목록, 기존 임의 공지, 비활성 버튼으로 대체 성공을 만들지 않는다.

| 회의 단계 | 검증                                                                                                                |
| --------- | ------------------------------------------------------------------------------------------------------------------- |
| M01–M03   | 지정 참여자·일시·장소·두 문단 본문 생성/재조회 및 문단별 수직 배치, 담당자·기한 액션, 같은 팀원 상세와 팀 액션 플랜 |
| M04–M06   | 관리자 분반/팀 링크·읽기 전용 본문, 다른 팀 직접 접근의 실제 서버 거부, 삭제 취소 후 보존                           |
| M07–M09   | 실제 편집 잠금으로 수정, 같은 ID의 팀원/관리자 재조회, 액션 링크 유지                                               |
| M10–M12   | 최종 UI 삭제, 팀장/팀원 목록·상세와 액션 연쇄 삭제, 관리자 목록·missing 상태                                        |

| 공지 단계 | 검증                                                                                              |
| --------- | ------------------------------------------------------------------------------------------------- |
| N01       | 새 분반에 즉시 텍스트 게시, 숫자 ID/분반을 UI 경로로 확보, 관리자 재조회                          |
| N02       | 일반 로그인 학생의 새 글 → 상세 → 목록 읽음, 동일 context의 브라우저 로컬 읽음 상태 재로딩 지속성 |
| N03       | 동일 공지·분반의 제목/본문 수정과 재조회 (N02 성공과 독립)                                        |
| N04       | 학생 재로딩 후 수정 본문, 원본 본문 부재; 공지는 잔여 대상으로 인계                               |

공지 구현/검증 전 `node .agent/scripts/openapi-contract.mjs status`와 `refresh`를 실행하고 atomic `current.json`의 GET `/api/v1/sections/{sectionId}/announcements`, POST 같은 경로, PATCH `/api/v1/announcements/{id}` 계약과 배포 SHA를 확인한다. 입력은 한 분반의 제목(192자 이하)/텍스트이며 즉시 게시 시 `publishedAt`을 생략한다. 생성 분반 수강생에게 알림이 발송되므로 이번 실행의 분반만 선택한다. 계약·서버·교수 소유권 문제는 N 범위의 실제 실패/차단으로 기록하고 다른 분기를 계속 진행한다.

첨부, 여러 분반 게시, 전체 공지 삭제, 다른 기기의 읽음 동기화, 수정 후 unread 정책, 회의–마일스톤 연결과 추가 P1 액션/잠금 시나리오는 제외한다.

서비스 없이 그래프·명단·URL 회귀를 검증하려면 `node --experimental-strip-types --test apps/oop/e2e/integrated/*.test.mjs`를 사용한다. `pnpm --filter @aics/oop test:e2e:integrated --list`는 라이브 변경 없이 단일 workflow 수집을 확인한다. `--grep`은 내부 단계 선택 기능이 아니다. 첫 새 데이터 실행이 유효하게 통과하면 두 번째 새 데이터 실행 또는 승인된 `--repeat-each=2` 최종 게이트를 사용한다. 실패 시 무한 재시도하지 않는다.

기존 `test:e2e:live`는 준비된 계정의 별도 회귀 suite다. 기존 공지 검증은 빈 목록에서 종료할 수 있고 생성/수정을 보장하지 않는다. 기존 회의 검증은 직접 API cleanup을 사용하므로 integrated 헬퍼로 가져오지 않는다. mocked `test:e2e:contract`는 UI 계약 회귀이며 실제 권한·영속성 증거와 구분한다.

## 실패 판정 시 주의

피드백은 입력창의 텍스트가 아니라 저장된 대화 항목을 확인한다. 중간 점검 수정 요청은 관리자 문서가 `REVISION_REQUESTED`로 재조회된 다음 학생이 편집한다. 버튼이 전송 중 비활성화된 상태만으로 성공을 판정하지 않는다. 제안서·중간 점검 제출 버튼은 필요한 상태 조회가 끝나야 활성화된다.

제안서 문서는 Project에 저장되므로 일반 Submission의 버전 0을 미작성으로 단정하지 않는다. 관리자 상세는 팀의 실제 프로젝트를 읽고, 제안서 피드백의 `relatedId`에는 프로젝트 ID를 사용한다. 중간 점검 반영 기록은 실제 중간보고서 ID를 사용한다. 일반 제출물 ID와 문서 ID는 서로 바꿔 쓸 수 없다.

`409 DATA_CONFLICT`는 성공으로 처리하거나 자동 재시도하지 않는다. UI에 실패가 남고 `outcomes.json`도 실패여야 한다. 현재 서버의 예외 처리에서 이 코드는 DB 제약조건 위반을 뜻하므로 서버 담당자가 해당 시각의 원인 로그와 제약조건을 확인해야 한다. 응답 코드를 다른 메시지 유형으로 우회하거나 일반 쪽지 전송으로 대체하면 제안서 피드백 통합 검증이 아니다.
