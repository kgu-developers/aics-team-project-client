# 브라우저만 사용하는 관리자·학생 통합 E2E

**“관리자·학생 통합 E2E 18단계를 검증해줘”**라고 요청하면 관리자 준비부터 학생 제출과 관리자 검토까지 한 흐름으로 실행한다. 관리자 계정만 미리 준비하면 학생 계정과 수강 등록, 팀 구성, 마일스톤은 모두 화면에서 만든다. 실행마다 새 강좌·분반을 사용한다.

Playwright의 `page.goto`, 클릭, 입력, 파일 선택과 화면 assertion으로만 진행한다. HTTP 클라이언트, `page.request`, `fetch`, API seed/cleanup, 응답 모킹, 인증 상태 주입은 사용하지 않는다. 테스트에서 XLSX/PDF/PNG 파일을 메모리에 만드는 것은 업로드할 파일 준비이며 서버 데이터 생성은 UI가 담당한다. 실패 분석용 네트워크 기록은 화면이 보낸 요청의 메서드·경로·상태 코드만 수집한다.

## 준비와 실행

저장소 루트 `.agent-local/e2e/integrated.env`에 아래 값을 설정한다. 파일 경로는 `OOP_E2E_INTEGRATED_ENV_FILE`로 바꿀 수 있고 같은 이름의 환경변수를 직접 설정해도 된다.

```dotenv
OOP_E2E_ADMIN_NUMBER=<관리자 학번>
OOP_E2E_ADMIN_PASSWORD=<관리자 비밀번호>
OOP_E2E_API_URL=https://api.example.test
# 이미 배포된 프런트엔드를 검사하려면 아래 값을 설정한다.
# OOP_E2E_BASE_URL=https://frontend.example.test
```

`OOP_E2E_BASE_URL`이 없으면 현재 브랜치의 Vite를 localhost:5173에 시작하고 API 프록시를 연결한다. 이미 실행 중인 서버를 자동으로 재사용하지 않는다. 원격 프런트엔드는 검사할 변경이 배포돼 있고 MSW가 꺼진 환경이어야 한다.

한 번은 “관리자·학생 통합 E2E 18단계를 검증해줘”, 반복 검증은 “새 데이터로 관리자·학생 통합 E2E 18단계를 두 번 연속 검증해줘”라고 요청한다. UI를 직접 보려면 “통합 E2E를 Playwright GUI로 열어줘”라고 요청한다. 아래는 에이전트 내부 실행·문제 해결용 참고다.

```sh
pnpm install
pnpm --filter @aics/oop exec playwright install chromium
pnpm test:e2e:integrated
# 새 데이터셋으로 전체 18단계를 연속 두 번 실행
pnpm --filter @aics/oop test:e2e:integrated --repeat-each=2
```

관리자는 강좌·분반 생성, 명단 업로드, 팀 배정 확정, 마일스톤·평가 관리 권한이 있어야 한다. 실제 데이터가 만들어지므로 테스트 전용 서버를 사용한다. 계정 비밀번호가 실행 trace에 남지 않도록 trace/video는 끈다. 자동 재시도는 하지 않는다.

## 로그인 계정

실행 폴더의 `dataset.json`이 해당 실행의 실제 값이다. 이름에 들어가는 `E2E248-<실행 시각>`으로 데이터 범위를 식별한다.

| 역할               | 로그인 시점                    | 팀과 용도                                                  |
| ------------------ | ------------------------------ | ---------------------------------------------------------- |
| 관리자             | 처음과 각 관리자 검토 단계     | 강좌·분반·학생·팀·마일스톤 준비, 피드백과 결과 조회        |
| `survey`           | 수강 등록 뒤, 팀 배정 전에     | 설문 제출과 배정 대기 확인. 팀 명단에서는 제외             |
| `leader`           | 팀 배정 확정 뒤                | 주제 확정, 제안서·중간 점검·발표·최종보고서 제출, 상호평가 |
| `memberA`          | 주제 투표와 최종보고서 제출 뒤 | 주제 투표·현재 제출 버전 승인                              |
| `memberB`          | 주제 투표와 최종보고서 제출 뒤 | 주제 투표·현재 제출 버전 승인                              |
| `memberC`          | 주제 투표와 최종보고서 제출 뒤 | 주제 투표·현재 제출 버전 승인                              |
| `comparisonLeader` | 발표 자료 제출 단계            | 비교팀 주제 확정과 발표 자료 업로드                        |
| `comparisonMember` | 비교팀 주제 확정 단계          | 대안 후보 등록·투표                                        |

학생 학번은 실행 시각에서 생성한 고유 문자열이며 실제 학번을 재사용하지 않는다. 학생 명단 업로드의 신규 계정 생성 계약에 따라 **연락처가 초기 비밀번호**가 된다. `dataset.json`의 `users.<역할>`에 학번·이름·이메일·연락처·초기 비밀번호가 함께 저장된다. 관리자 비밀번호는 데이터셋에 복사하지 않는다. 계정마다 별도 브라우저 context를 사용하므로 서로의 세션을 덮어쓰지 않는다.

## 데이터셋과 수동 재생성

실행 자료는 `.agent-local/e2e/integrated/runs/<실행 키>/`에 저장한다.

- `dataset.json`: 실행 키, 강좌·분반·팀명, 합성 계정 7개와 입력값, 날짜.
- `*-students.xlsx`: 학번/이름/이메일/연락처/역할의 7개 행. 관리자 학생 명단 업로드용.
- `*-teams.xlsx`: 팀명/학번/이름/팀장/역할의 6개 행. 관리자 팀 명단 업로드용.
- `reset-targets.json`: 해당 실행의 초기화 대상 계정·팀·분반과 의존성 순서. 서버 담당자 확인용이며 삭제를 실행하지 않는다.
- `e2e-submission.pdf`: 발표·최종보고서 수동 업로드에 사용할 PDF.
- `milestones.json`: 화면 링크에서 확인한 마일스톤 경로. 서버 재생성 후에는 새 값을 사용한다.
- `network.json`: UI 요청의 메서드·경로·상태 코드. 원문 응답, 인증 헤더, 토큰은 기록하지 않는다.
- `outcomes.json`: 단계별 통과/실패/선행 실패로 인한 미실행과 사유.
- 실패 시 `<단계>-actor-*.txt`와 `.png`: 각 실패 시점의 계정별 화면. 본문의 URL을 제거하고, 서명 URL을 포함할 수 있는 관리자 원시 문서 영역은 캡처에서 가린다. 독립 단계가 진행되어도 이전 실패 화면은 보존한다.
- `browser-errors.json`: 브라우저 JavaScript 오류 목록.

계정 JSON과 XLSX에는 초기 비밀번호로 사용하는 연락처가 있으므로 실행 폴더는 Git에 넣지 않는다. 수동 재현을 함께할 서버 담당자에게는 필요한 실행 폴더를 별도로 전달한다.

**매번 처음부터 실행할 때:** “새 데이터로 통합 E2E를 다시 검증해줘”라고 요청하면 새 학번·새 강좌·새 분반·새 팀을 만든다. 이전 제출 데이터를 삭제하거나 되돌릴 필요가 없다. 자동 정리는 없으며, 성공·실패 실행의 데이터는 서버에 남는다.

**같은 데이터셋을 수동 재생성할 때:** 서버 담당자가 먼저 해당 실행 키에 속한 데이터만 초기화했는지 확인한 뒤 학생·팀 XLSX를 위 순서대로 다시 업로드한다. 제출 버전·파일 연결·확인 기록·문서 영역 완료·수정 요청·평가 응답까지 정리해야 같은 초기 상태가 된다. 팀장 확정과 프로젝트 생성도 다시 진행한다. 마일스톤/팀/프로젝트/제출물 ID는 새 값이 생기므로 예전 숫자 ID를 재사용하지 않는다. `dataset.json`의 날짜가 지났다면 현재 기준으로 다시 잡는다.

브라우저에는 제출 완료·설문·평가 전체를 원상복구하는 통합 기능이 없다. 따라서 자동화는 초기화용 비공개 API를 호출하지 않는다. 기존 서버 ID를 보존해야 하는 초기화는 [기존 초기화 가이드](./reset-and-seed.md)의 범위와 의존성 순서를 서버 담당자와 함께 적용한다. 단순 탈퇴·재활성화나 팀원 승인 취소만으로 제출 이력이 초기화되지는 않는다.

## 결과 해석

HTML 보고서는 `.agent-local/playwright/integrated-report/index.html`에 생긴다. 이 suite는 상태가 이어지는 하나의 테스트 안에 18개 단계를 둔다. 01~06 공통 준비가 실패하면 이후 실행을 중단한다. 이후에는 실패한 단계에 의존하는 단계만 건너뛴다(08←07, 10←09, 12←11, 13←12, 15/16←14, 18←17). 독립된 제출 흐름은 계속 확인하고, 실패가 하나라도 있으면 suite는 실패로 종료한다. 건너뛴 단계는 통과에 포함하지 않는다.

기존 학생 suite와 API 계약 기반 suite는 각각 `pnpm test:e2e:live`, `pnpm test:e2e:contract`로 유지한다. 공지, 회의록 CRUD, 모바일 탐색, 편집 잠금 같은 개별 회귀 검증은 기존 suite에 있다. 통합 suite의 통과가 모든 화면이나 모든 브라우저의 통과를 뜻하지 않는다.

## 실패 판정 시 주의

피드백은 입력창의 텍스트가 아니라 저장된 대화 항목을 확인한다. 중간 점검 수정 요청은 관리자 문서가 `REVISION_REQUESTED`로 재조회된 다음 학생이 편집한다. 버튼이 전송 중 비활성화된 상태만으로 성공을 판정하지 않는다. 제안서·중간 점검 제출 버튼은 필요한 상태 조회가 끝나야 활성화된다.

제안서 문서는 Project에 저장되므로 일반 Submission의 버전 0을 미작성으로 단정하지 않는다. 관리자 상세는 팀의 실제 프로젝트를 읽고, 제안서 피드백의 `relatedId`에는 프로젝트 ID를 사용한다. 중간 점검 반영 기록은 실제 중간보고서 ID를 사용한다. 일반 제출물 ID와 문서 ID는 서로 바꿔 쓸 수 없다.

`409 DATA_CONFLICT`는 성공으로 처리하거나 자동 재시도하지 않는다. UI에 실패가 남고 `outcomes.json`도 실패여야 한다. 현재 서버의 예외 처리에서 이 코드는 DB 제약조건 위반을 뜻하므로 서버 담당자가 해당 시각의 원인 로그와 제약조건을 확인해야 한다. 응답 코드를 다른 메시지 유형으로 우회하거나 일반 쪽지 전송으로 대체하면 제안서 피드백 통합 검증이 아니다.
