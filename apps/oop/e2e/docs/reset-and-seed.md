# 테스트 팀2 생성·초기화 데이터 명세

관리자 화면에서 데이터 생성부터 진행하는 새 통합 suite는 [브라우저 통합 E2E 가이드](./integrated.md)를 따른다. 이 문서는 기존 학생 전용 suite의 고정 데이터셋 기준이다.

서버 담당자가 관리자 화면, Swagger 또는 서버의 seed 작업으로 동일한 시작 상태를 만들기 위한 문서다. [유저 플로우](./user-flows.md)를 먼저 읽고, [team2.seed.json](../datasets/team2.seed.json)을 입력값의 기준으로 사용한다.

이 JSON은 **수동 생성 명세**다. DB 덤프, 실행 스크립트, 단일 API 요청 본문이 아니다. 각 `createBody` 등을 해당 요청에 사용하고 `{{...}}` 자리는 실제 값으로 치환한다. `baseline`은 생성·초기화 후 확인할 상태이며 DB에 그대로 PATCH할 객체가 아니다. 실제 DB 테이블명과 외래키 구조는 이 클라이언트 저장소에서 확인할 수 없으므로 SQL 삭제문은 제공하지 않는다.

## 1. 재현할 데이터 구성

| 대상                       | 수량 | 시작 상태                                                              |
| -------------------------- | ---- | ---------------------------------------------------------------------- |
| OOP 분반                   | 1    | ACTIVE 학생 수강 7명, 팀 배정 확정, 정원 20                            |
| 합성 학생 계정             | 7    | 로그인 가능, 각자 ACTIVE 학생 분반 1개                                 |
| 테스트 팀2                 | 1    | L/A/B/C 4명, L 팀장 확정                                               |
| 테스트 팀2 비교팀          | 1    | CL/CM 2명, CL 팀장 확정                                                |
| 설문 학생 S                | 1    | 같은 분반, 팀 미배정, 사전 설문 응답 없음                              |
| 프로젝트                   | 2    | 각 팀에 확정 주제·내용 저장, 제안서 미제출                             |
| 마일스톤                   | 5    | PROPOSAL, MID_REPORT, PRESENTATION, FINAL_REPORT, PEER_EVALUATION 공개 |
| 필수 산출물                | 2    | 발표·최종보고서에 PDF 1개씩, 5MB 이하                                  |
| 상호평가 폼                | 1    | 익명, 열린 기간, 응답 0개                                              |
| 회의록·액션·공지·발표 평가 | 0    | 이 데이터셋에는 생성하지 않음                                          |
| 파일 제출 버전·팀원 승인   | 0    | 미제출, 최종 완료 아님                                                 |

역할 L/A 등과 학번은 [계정 표](./user-flows.md#1-로그인-계정)를 참조한다. 관리자 유저 생성 API의 `globalRole`은 `USER`, 수강 등록의 `role`은 `STUDENT`다. 로그인 후의 역할이 STUDENT로 확인돼야 한다.

초기 일정은 작성 시작 `2026-09-01T00:00:00`, 마감 `2027-02-01T23:59:59`, 연락처 공개 종료 `2027-03-01T00:00:00`이다. 이후 재생성 시에는 실제 실행 시각이 작성·제출·평가 기간 안에 있도록 날짜를 함께 갱신한다. API 날짜 문자열에는 offset이 없으므로 서버의 시간대 해석을 확인하고, 이 데이터셋의 기준 시간대는 Asia/Seoul로 맞춘다.

발표 평가 기간은 기본값에서 설정하지 않는다. 현재 자동화는 발표 자료 업로드를 검증한다. 발표 평가까지 추가할 때는 평가 항목과 평가 시작·종료를 별도로 준비한다. 발표 평가 시작을 제출 마감보다 앞에 두는 설정은 이 서버에서 거절됐으므로 그대로 복사하지 않는다.

## 2. 수동 생성 순서

### 준비: 환경과 ID 기록

API 서버 주소, 프런트엔드 주소, 담당 교수 ID, 실제 OOP course ID, 테스트 비밀번호를 준비한다. JSON의 course ID 1은 이전 실행의 기준값이므로 다른 서버에서는 조회해서 바꾼다.

생성 응답의 ID는 다음 표에 기록한다. 같은 이름으로 재생성해도 숫자 ID가 같아진다고 가정하지 않는다.

| 논리 키                                                                     | 기록할 값                                      |
| --------------------------------------------------------------------------- | ---------------------------------------------- |
| `section`                                                                   | 생성한 분반 ID                                 |
| `team2`, `comparison`                                                       | 팀 목록에서 이름과 구성원을 확인한 팀 ID       |
| `project.team2`, `project.comparison`                                       | 각 팀 프로젝트 ID                              |
| `PROPOSAL`, `MID_REPORT`, `PRESENTATION`, `FINAL_REPORT`, `PEER_EVALUATION` | 각 마일스톤 ID                                 |
| `peerForm`                                                                  | 상호평가 폼 ID                                 |
| `requiredArtifact.PRESENTATION`, `requiredArtifact.FINAL_REPORT`            | 필수 산출물 ID                                 |
| `topicCandidate.team2`, `topicCandidate.comparison`                         | 확정에 사용한 주제 후보 ID                     |
| `submission.*`, `midReport`                                                 | 조회/제출 과정에서 생긴 ID; 초기화 범위 확인용 |

숫자 타입 ID를 JSON 본문에 넣을 때는 `"{{candidateId}}"` 같은 자리표시자를 **실제 정수 값**으로 바꾼다. 학번·교수 ID는 문자열이다.

### ① 관리자 로그인, 분반과 학생 생성

관리자 계정으로 로그인한 세션에서 아래 요청을 수행한다. 브라우저 UI로 가능한 항목은 같은 필드로 입력해도 된다. 직접 요청할 경우 로그인 API의 쿠키·access token·CSRF 계약을 따른다.

| 순서 | 요청                                                          | 데이터셋에서 가져올 본문 / 확인                 |
| ---- | ------------------------------------------------------------- | ----------------------------------------------- |
| 1    | `POST /api/v1/oop/auth/login`                                 | 관리자 `studentNumber`, `password`              |
| 2    | `POST /api/v1/admin/oop/sections`                             | `section.createBody`; 담당 교수 자리표시자 치환 |
| 3    | `POST /api/v1/admin/oop/users` × 7                            | `users[].createBody`; 테스트 비밀번호 치환      |
| 4    | `POST /api/v1/admin/oop/sections/{sectionId}/enrollments` × 7 | 각 `studentNumber`와 `role: "STUDENT"`          |
| 5    | `GET /api/v1/admin/oop/sections/{sectionId}/enrollments`      | 7명 모두 ACTIVE STUDENT인지 확인                |

이미 존재하는 학번은 이름만 보고 덮어쓰지 않는다. 이 데이터셋의 합성 계정인지 확인한 뒤 기존 계정을 재사용하거나 다른 합성 학번 7개를 배정한다. 탈퇴 후 재활성화(`reactivate`)는 제출 이력 초기화의 대체 수단으로 사용하지 않는다.

### ② 팀 명단 반영과 확정

관리자 팀 명단 업로드에서 다음 5개 열을 갖는 XLSX를 사용한다. 실제 행은 JSON의 `teamImport.rows`에 있다. 전달 ZIP에는 이전 생성에 사용해 미리보기·반영까지 성공한 `team2-team-import.xlsx`도 포함된다.

| 팀명              | 학번      | 이름            | 팀장 | 역할 |
| ----------------- | --------- | --------------- | ---- | ---- |
| 테스트 팀2        | 209900201 | E2E 팀2 팀장    | Y    | 팀장 |
| 테스트 팀2        | 209900202 | E2E 팀2 팀원A   |      | 개발 |
| 테스트 팀2        | 209900203 | E2E 팀2 팀원B   |      | 개발 |
| 테스트 팀2        | 209900204 | E2E 팀2 팀원C   |      | 개발 |
| 테스트 팀2 비교팀 | 209900205 | E2E 비교팀 팀장 | Y    | 팀장 |
| 테스트 팀2 비교팀 | 209900206 | E2E 비교팀 팀원 |      | 개발 |

학번 셀은 문자열로 유지한다. S(209900207)는 명단에 넣지 않는다. 다른 학번으로 재생성할 때는 XLSX도 수정해야 한다.

1. `POST /api/v1/admin/oop/sections/{sectionId}/team-imports/preview`에 XLSX를 multipart의 `file`로 보낸다.
2. 미리보기에서 **전체 6행 / 유효 6행 / 오류 0행**과 팀장 두 명을 확인한다.
3. 반환된 `importId`로 `POST /api/v1/admin/oop/team-imports/{importId}/apply`를 호출한다.
4. `GET /api/v1/admin/oop/sections/{sectionId}/teams`로 두 팀 ID와 인원을 기록한다.
5. **새 E2E 전용 분반**의 `PATCH /api/v1/admin/oop/sections/{sectionId}/teams/finalize`를 호출한다.
6. L/CL로 로그인해 팀장 상태를 확인한다. 팀장 확정이 끝나지 않았다면 각 팀장이 온보딩에서 확정한다. 공개 API는 `POST /api/v1/oop/teams/{teamId}/leader-claim`이다. 이미 확정된 팀에 다시 호출할 필요는 없다.

### ③ 마일스톤과 평가 폼 생성

관리자 세션에서 다음 순서로 처리한다.

1. JSON의 `milestones` 5개 각각에 대해 `POST /api/v1/admin/oop/sections/{sectionId}/milestones`에 `createBody`를 보낸다.
2. 반환 ID별로 `PATCH /api/v1/admin/oop/sections/{sectionId}/milestones/{milestoneId}/status`에 `publishBody`(`PUBLISHED`)를 보낸다.
3. PRESENTATION과 FINAL_REPORT에만 `POST /api/v1/admin/oop/sections/{sectionId}/milestones/{milestoneId}/required-artifacts`로 `requiredArtifacts`의 PDF 항목을 등록한다.
4. `POST /api/v1/admin/oop/sections/{sectionId}/peer-evaluation-forms`로 `peerEvaluationForm.createBody`를 보낸다. `milestoneId`를 실제 PEER_EVALUATION ID로 치환한다.
5. 기존 분반을 재사용하는 경우 같은 종류의 마일스톤/열린 상호평가 폼이 중복되지 않도록 확인한다. 테스트는 학생 평가 컨텍스트가 선택한 폼을 사용하며 별도 `OOP_E2E_PEER_FORM_ID` 설정으로 폼을 강제하지 않는다.

### ④ 각 팀장으로 프로젝트 준비

관리자 대신 **L**, 이어서 **CL**로 로그인해 각자의 팀을 처리한다. 데이터셋의 `projects`에 팀별로 본문이 들어 있다.

1. `POST /api/v1/teams/{teamId}/topic-candidates`에 `candidateBody`를 보내 주제 후보를 만든다.
2. 반환된 후보 ID로 `PATCH /api/v1/teams/{teamId}/topic-finalize`에 `finalizeBody`를 보낸다. 팀장은 L/CL, 목표는 `학생 사용자 기능을 검증한다`다.
3. `GET /api/v1/teams/{teamId}/project`에서 프로젝트 ID를 기록한다.
4. `PUT /api/v1/teams/{teamId}/project`에 `updateBody`를 보내 제목·설명·목표, 도서 데이터 행, 도서 목록 화면 행, 프로젝트 일정·팀 규칙·회의 일정을 저장한다.
5. 제안서 영역은 작성 중 상태로 유지한다. `proposal-complete`를 호출하지 않는다. 화면 이미지 `imageFileId`는 기본값 null이며 현재 20개는 이미지 업로드나 제안서 최종 제출을 요구하지 않는다.
6. L의 `/student/editor/mid-review/topic`을 열어 중간보고서가 DRAFT로 열리는지 확인한다. `GET /mid-reports/current`는 문서가 없으면 생성할 수 있으므로 생성된 ID도 기록한다. API 버전 값은 조회 응답을 사용하고 0/1로 하드코딩하지 않는다.

### ⑤ Playwright 환경변수 연결

저장소 루트 `.agent-local/e2e/live.env`에 기록한다. 실제 비밀번호는 이 로컬 파일에만 넣고 공유 문서에는 넣지 않는다.

```dotenv
OOP_E2E_BASE_URL=http://localhost:5173
OOP_E2E_API_URL=<실제 API 서버 주소>
OOP_E2E_STUDENT_NUMBER=209900201
OOP_E2E_PASSWORD=<L 비밀번호>
OOP_E2E_MEMBER_NUMBER=209900202
OOP_E2E_MEMBER_PASSWORD=<A 비밀번호>
OOP_E2E_SURVEY_NUMBER=209900207
OOP_E2E_SURVEY_PASSWORD=<S 비밀번호>
OOP_E2E_TEAM_ID=<team2 ID>
OOP_E2E_SECTION_ID=<section ID>
OOP_E2E_PRESENTATION_ID=<PRESENTATION ID>
OOP_E2E_FINAL_REPORT_ID=<FINAL_REPORT ID>
```

기존 프런트엔드를 사용하면 `OOP_E2E_BASE_URL`을 지정한다. 자동으로 Vite를 띄우려면 BASE_URL을 생략하고 API_URL을 설정한다. 앱의 MSW는 꺼야 하고, API가 프런트엔드 origin을 허용해야 한다. 현재 config의 자동 Vite 포트는 localhost:5173이다.

## 3. 초기화 완료 판정

아래 상태가 모두 맞아야 **20개 전체의 시작 상태**가 복원된 것이다. 로그아웃하거나 파일을 재제출한 것만으로 이 상태가 만들어지지는 않는다.

| 계정 / 조회                                                            | 확인할 상태                                                                              |
| ---------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| L/A의 `GET /api/v1/oop/users/me`                                       | 정확한 학번, 같은 E2E 분반 1개, 같은 테스트 팀2 ID                                       |
| S의 `/me`                                                              | E2E 분반, teamId null                                                                    |
| S의 `GET /api/v1/oop/users/me/pre-survey-response`                     | 미제출에 해당하는 404; 로그인 화면에서 설문 `시작하기` 가능                              |
| L/CL의 프로젝트 조회                                                   | JSON의 원문, `approvalStatus: DRAFT`, `proposalCompletedAt: null`                        |
| 제안서 영역 조회                                                       | 모든 영역 completed false, 현재 편집 잠금 없음                                           |
| 중간보고서 최초 조회                                                   | DRAFT, submittedAt null, 완료 블록 없음, 편집 가능                                       |
| L의 발표·최종보고서 `GET /milestones/{milestoneId}/my-team-submission` | currentVersion 0, NOT_SUBMITTED, canSubmitNow true; 조회 시 생성되는 제출 루트 행은 허용 |
| 제출의 버전·승인·완료 상태                                             | 버전 이력 0, 승인 0, completedAt null, 대기 중 리뷰 없음                                 |
| L/A의 평가 화면                                                        | 열린 폼의 대상 3명, 기존 최종 제출 없음; 완전 초기화에서는 초안도 없음                   |
| E2E 분반의 팀·학생 목록                                                | 2팀, 총 6명 배정, S 1명 미배정                                                           |
| 회의록·액션                                                            | 이 테스트 실행에서 남은 레코드 없음                                                      |

파일 제출은 조회 과정에서 제출 루트 행이 생성될 수 있다. 따라서 루트 행 수를 무조건 0으로 고정하기보다 **버전 0·미제출·승인 없음**을 확인한다. 중간보고서도 최초 조회로 생성되는 것은 정상이다.

## 4. 제출 후 초기화

### A. 기존 이력을 유지하며 반복하기

설문 S와 상호평가 최종 제출 L을 제외한 18개는 다음 조건에서 반복할 수 있다.

- 제안서·중간보고서는 미제출이며 편집 잠금이 해제돼 있다.
- A의 상호평가는 초안이고, 최종보고서 승인은 취소돼 있다.
- 발표·최종보고서의 제출 기간이 열려 있고 재제출이 허용된다. 단계는 최종 완료되지 않았다.
- 파일 테스트가 이전 버전+1을 확인하므로 기존 파일 버전을 삭제하지 않아도 된다.

이 방식은 전체 데이터 초기화가 아니다. 이력 보존이 목적일 때 사용하는 반복 실행 조건이다.

### B. 서버 담당자와 전체 시작 상태 복원하기

1. 이 데이터셋에 연결된 분반 ID, 7개 학번, 2개 팀 ID와 모든 하위 ID를 기록한다. 진행 중인 E2E와 편집 브라우저 창을 종료한다.
2. 서버 담당자가 이 범위를 기준으로 실제 FK·스토리지 참조를 조회한다. 다른 분반/팀의 기록이 연결돼 있으면 범위를 분리한다.
3. 아래 표의 종속 데이터부터 정리하고 부모의 제출·문서 상태를 복원한다. 구체적인 삭제 순서는 실제 서버 스키마의 FK 순서를 따른다.
4. 프로젝트 내용과 팀 운영 정보를 JSON으로 다시 채운다. 분반·계정·팀·마일스톤·평가 폼은 재사용해도 되고 새로 만들어도 된다.
5. 새로 만들어진 ID를 환경변수에 갱신하고 브라우저 세션을 새로 시작한다.
6. 3절의 완료 판정을 확인한 뒤 `OOP_E2E_SUBMIT=1 pnpm test:e2e`를 실행한다.

기존 테스트가 정상 종료했다면 제안서 제목·중간보고서 설명·A의 승인·새 회의록은 정리된다. 그러나 파일 이력, 평가 초안, 제출된 설문·상호평가, 저장 버전과 감사 이력은 남는다. 감사 로그의 보존은 서버 정책에 따른다. 기능 재현을 위해 다른 사용자 기록이나 전체 감사 로그를 삭제할 필요는 없다.

업로드 파일은 DB의 첨부 참조만 지운다고 객체 스토리지에서 사라지지 않는다. 서버 담당자가 해당 테스트 파일 ID/객체 키의 참조를 확인하고, 공유되지 않는 테스트 객체만 정리한다. 파일명이나 분반명 접두사만으로 스토리지를 일괄 삭제하지 않는다.

### C. 새 분반·계정으로 수동 재생성하기

DB 초기화 작업 없이 같은 플로우를 다시 만들려면 새 E2E 분반과 새로운 합성 계정 7개로 2절을 반복한다. 기존 데이터는 이력으로 남는다.

1. 분반 코드에 실행 식별자를 붙이고, 사용 가능한 학번 7개와 이메일을 정한다.
2. JSON의 `section.createBody.code`, `users[].createBody`, `teamImport.rows`를 함께 수정한다. XLSX와 환경변수도 동일하게 맞춘다.
3. 기존 계정을 새 분반에 중복 등록하는 방법은 피한다. 현재 학생 온보딩은 배정 팀과 단일 수강 분반의 일치를 확인하므로 여러 ACTIVE 분반이 생기면 홈 진입 조건이 달라진다.
4. 새 팀·프로젝트·마일스톤·평가 폼 ID를 기록한다. 현재 서버의 숫자 ID를 복사하지 않는다.
5. S의 응답이 없고 L/A가 새 폼의 미제출 상태인지 확인한다.

### 재오픈과 초기화의 차이

공개 계약에 `PATCH /submissions/{submissionId}/reopen`이 있다. 담당 교수가 미래의 `revisionDueAt`을 지정해 완료된 단계를 다시 제출 가능하게 여는 기능이다. **과거 버전·파일·평가 응답을 지우는 전체 초기화 API가 아니다.** 사전 설문/상호평가를 미제출로 만들 때 사용할 수 없다.

분반 삭제 API도 있지만, 분반 삭제가 학생 계정·파일·설문·모든 하위 이력을 원하는 방식으로 정리한다는 계약은 확인하지 못했다. 분반 DELETE 한 번을 전체 초기화 절차로 안내하지 않는다.

## 5. 제출 후 결과 기록

[team2.after-full-run.json](../datasets/team2.after-full-run.json)은 **새 baseline에서 20개 전체를 한 번 실행한 뒤**의 기대 상태다. S 설문 있음, L 상호평가 제출, A 초안, 발표·최종보고서 버전 1, 최종보고서 L만 승인, 단계 미완료가 기준이다. 기존 데이터에서 재실행했다면 파일 버전은 1보다 클 수 있다.

실행 일시, 앱/서버 버전, 사용 분반·팀·폼 ID, 시작 버전→종료 버전, 성공/실패 시나리오, 정리하지 못한 ID를 함께 기록하면 다음 초기화 때 범위를 특정할 수 있다. Playwright 출력·스크린샷은 `.agent-local/playwright/` 아래에 저장된다.

이 문서의 API 경로·필드는 2026-09-13에 확보한 OpenAPI와 실제 생성에 사용한 요청을 기준으로 정리했다. 생성 경로는 앞선 실서버 데이터 준비에서 사용했다. 서버 DB 직접 초기화·새 번호로 재생성은 이 문서 작성 중 실행하지 않았으며 서버 스키마에 맞춘 작업과 확인이 필요하다.
