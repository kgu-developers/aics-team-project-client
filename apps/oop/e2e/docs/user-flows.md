# OOP 학생 E2E 수동 실행 가이드

관리자 화면에서 데이터 생성부터 진행하는 새 통합 suite는 [브라우저 통합 E2E 가이드](./integrated.md)를 따른다. 이 문서는 기존 학생 전용 suite의 고정 데이터셋 기준이다.

이 문서는 `e2e/live`의 실서버 테스트 20개를 사람이 같은 순서와 입력으로 재현하기 위한 안내다. 계정 준비는 [데이터 생성·초기화 가이드](./reset-and-seed.md), 입력값 원본은 [team2.seed.json](../datasets/team2.seed.json)을 사용한다.

## 1. 로그인 계정

아래 학번은 이번 테스트를 위해 만든 합성 계정이다. 새 서버에서 번호가 겹치면 데이터셋의 학번을 모두 새 번호로 바꾸고 팀 명단·실행 환경변수도 함께 갱신한다.

| 별칭   | 학번               | 이름                         | 사용할 기능                                                   |
| ------ | ------------------ | ---------------------------- | ------------------------------------------------------------- |
| 관리자 | 환경별 관리자 계정 | 담당 교수 권한이 있는 관리자 | 분반·학생·팀·마일스톤·평가 폼 준비                            |
| L      | 209900201          | E2E 팀2 팀장                 | 홈, 제안서, 중간보고서, 회의록, 파일 제출, 상호평가 최종 제출 |
| A      | 209900202          | E2E 팀2 팀원A                | 두 계정 편집 잠금, 상호평가 초안, 최종보고서 승인·취소        |
| B      | 209900203          | E2E 팀2 팀원B                | 상호평가 대상, 추가 수동 최종 승인                            |
| C      | 209900204          | E2E 팀2 팀원C                | 상호평가 대상, 추가 수동 최종 승인                            |
| CL     | 209900205          | E2E 비교팀 팀장              | 비교팀 프로젝트 준비                                          |
| CM     | 209900206          | E2E 비교팀 팀원              | 비교팀 구성                                                   |
| S      | 209900207          | E2E 설문 학생                | 팀 배정 전 사전 설문                                          |

L/A/B/C는 **테스트 팀2**, CL/CM은 **테스트 팀2 비교팀**에 배정한다. S는 같은 분반의 수강생이지만 **팀에 배정하지 않는다**. 각 계정은 이 테스트 분반 하나에만 ACTIVE 학생 수강 상태를 갖게 한다. 비교팀 간 접근 차단·발표 평가는 현재 20개에 포함되지 않는다.

기존 계정 비밀번호는 저장소 루트의 `.agent-local/e2e/accounts.json`에서 확인한다. 새로 생성할 때는 서버 담당자와 정한 테스트 전용 비밀번호를 사용하고 별도로 전달한다. 공유용 JSON의 `{{E2E_SEED_PASSWORD}}`는 실제 비밀번호로 치환해야 하는 자리다.

두 계정 동시 테스트는 일반 창과 시크릿 창 또는 서로 다른 브라우저 프로필을 사용한다. 같은 프로필의 탭 두 개는 로그인 쿠키를 공유하므로 L/A 분리 테스트가 되지 않는다.

## 2. 시작 조건과 권장 순서

관리자가 분반·팀을 만들고 팀 배정을 확정한 뒤, L과 CL의 팀장 확정 및 프로젝트 생성을 완료한다. 제안서·중간보고서는 미제출, 발표·최종보고서는 제출 버전 0, 사전 설문과 상호평가는 미제출 상태로 시작한다.

현재 만들어 둔 서버 데이터는 이미 실행한 이력이 있다. **S의 설문과 L의 상호평가는 제출 완료 상태**이므로 해당 두 시나리오는 초기화 후 실행한다. 파일 제출은 제출 기간이 열려 있고 최종 완료 전이면 재제출로 반복할 수 있다.

| 순서 | 플로우                    | 로그인       | 자동 테스트 수 | 실행 후 처리                        |
| ---- | ------------------------- | ------------ | -------------- | ----------------------------------- |
| F01  | 로그인·접근·로그아웃      | 미로그인 → L | 6              | 로그아웃                            |
| F02  | 홈과 모바일 메뉴          | L            | 2              | 변경 없음                           |
| F03  | 공지사항                  | L            | 1              | 현재 데이터에서는 빈 목록 확인      |
| F04  | 사전 설문 제출            | S            | 1              | 응답이 남음; 다시 실행하려면 초기화 |
| F05  | 제안서 저장·이동·잠금     | L, A         | 3              | 원문 복원, 두 계정 편집 화면 종료   |
| F06  | 중간보고서 자동 저장      | L            | 1              | 원문 복원                           |
| F07  | 회의록·액션               | L            | 1              | 방금 만든 회의록 삭제               |
| F08  | 상호평가 초안·최종 제출   | A → L        | 2              | A 초안 유지, L 제출 상태 유지       |
| F09  | 발표·최종보고서 파일 제출 | L            | 2              | 파일과 버전 이력이 남음             |
| F10  | 최종보고서 승인·취소      | A            | 1              | A의 승인 취소                       |

F04는 독립적인 미배정 학생 플로우다. S를 팀에 넣어 다음 플로우까지 이어가는 시나리오가 아니다. F10은 F09의 최종보고서 제출 뒤에 실행한다. 그 외 시나리오는 각 시작 조건을 만족하면 독립적으로 실행할 수 있다.

## F01. 로그인·직접 접근·세션 복원

**계정:** 미로그인, L. **대응 코드:** `live/student.spec.ts`.

1. 로그아웃한 새 브라우저 창에서 `/student`, `/student/team`, `/student/meetings`, `/student/editor/proposal/topic`을 각각 연다. 각 주소에서 로그인 화면으로 이동하는지 확인한다.
2. L의 학번과 `invalid-e2e-password`를 입력한다. 로그인 화면에 오류가 표시돼야 한다. 개발자 도구 Network에서 로그인 API가 401인지 확인할 수 있다.
3. L의 올바른 비밀번호로 로그인한다. 학생 홈 `/student`와 `학생 홈 바로가기` 탭이 보여야 한다.
4. 새로고침한다. 다시 로그인하지 않고 학생 홈이 유지돼야 한다. 자동 테스트는 refresh API의 200 응답과 `refreshToken` 쿠키의 HttpOnly 속성도 확인한다.
5. `내 프로필 열기`에서 L의 학번을 확인하고 `로그아웃`을 누른다. `/student`를 다시 열어도 로그인 화면으로 이동해야 한다.

이 검증은 학생 경로의 접근 가드와 세션 동작에 대한 것이다. 관리자 경로나 타 분반 데이터 전체의 권한 검증을 대신하지 않는다.

## F02. 홈 탭과 모바일 메뉴

**계정:** L. **대응 코드:** `live/student.spec.ts`.

1. 학생 홈에서 `공지사항` 탭에 키보드 포커스를 둔다.
2. 오른쪽 화살표를 누르면 `회의록`, End 키를 누르면 `액션 플랜`이 선택돼야 한다.
3. 브라우저를 390×844 크기로 바꾼다. 모바일 메뉴를 열고 `액션 플랜`을 선택한다.
4. `팀 액션 플랜` 제목과 화면이 표시되는지 확인한다.

## F03. 공지사항

**계정:** L. **대응 코드:** `live/student.spec.ts`.

1. 학생 메뉴에서 `공지사항`으로 이동한다.
2. 기본 데이터셋에는 공지가 없다. `등록된 공지사항이 없어요.`가 보여야 한다.
3. 해당 분반에 공지를 별도로 준비한 환경에서는 제목을 눌러 본문을 확인하고 목록으로 돌아온다. 읽은 공지의 `새 글` 표시가 없어져야 한다.

이번 실서버 실행에서는 2번만 검증했다. 공지 생성은 기본 데이터셋에 포함하지 않는다.

## F04. 팀 배정 전 사전 설문 제출

**계정:** S. **시작 조건:** 팀 미배정, 사전 설문 응답 없음. **대응 코드:** `live/onboarding.spec.ts`, `@submit`.

1. S로 로그인하고 설문 화면에서 `시작하기`를 누른다.
2. 역할을 선택하기 전에는 `다음 설문`을 누를 수 없어야 한다.
3. `개발`을 체크하고 `다음 설문`을 누른다. 서버 값은 `DEVELOPMENT`다.
4. `프로젝트 주제 아이디어`에 `E2E 도서 관리 프로그램`, `요청 또는 메모`에 `테스트 전용 설문 응답`을 입력한다. 조원 지목은 하지 않는다.
5. `설문 제출` → `설문 제출 확인` 대화상자의 `제출`을 누른다.
6. `설문에 응답해 주셔서 감사합니다.` 화면이 보여야 한다. 새로고침해도 같은 팀 배정 대기 화면을 유지해야 한다.

**남는 데이터:** S의 사전 설문 응답. 로그아웃·쿠키 삭제로 응답이 초기화되지 않는다.

## F05. 제안서 작성·저장·동시 편집 잠금

**계정:** L, 잠금 검증에 A. **시작 조건:** 프로젝트 존재, 제안서 미제출. **대응 코드:** `live/documents.spec.ts`의 앞 3개.

1. L로 로그인한다. 홈의 제안서 작성 링크를 눌러 `/student/editor/proposal/topic`으로 이동한다.
2. `프로젝트 제목`의 원문 `테스트 팀2 도서 관리`를 기록하고 `E2E 저장 확인 <실행시각>`으로 바꾼다.
3. `저장`을 누른다. `제안서를 저장했어요.`가 표시되고 새로고침 후에도 바뀐 제목이 남아야 한다.
4. 원래 제목으로 다시 저장한다. 이 테스트에서는 `작성 완료`나 제안서 `제출하기`를 누르지 않는다.
5. L이 주제 편집 화면을 열어 둔 상태에서 별도 브라우저 프로필로 A에 로그인한다. A도 같은 제안서 주제 화면을 연다.
6. A 화면에서 `편집 중` 안내가 표시되고 제목 수정과 `저장`이 비활성화돼야 한다.
7. A 창을 닫고 L도 학생 홈으로 이동한다. 이후 편집을 막는 잠금이 남지 않아야 한다.
8. L로 `/student/editor/mid-review/topic`을 열어 `1. 주제` 제목을 확인한다. `/student/team`을 열어 L의 학번이 팀원 목록에 있는지 확인한다.

**남는 데이터:** 원문은 복원하지만 서버의 저장 이력·갱신 시각까지 이전 상태로 되돌리지는 않는다. 영역 저장은 작성 완료 상태를 해제할 수 있어 작성 중 프로젝트를 사용한다.

## F06. 중간보고서 자동 저장

**계정:** L. **시작 조건:** MID_REPORT 마일스톤 공개·작성 기간 내, 문서 미제출. **대응 코드:** `live/documents.spec.ts`의 마지막 테스트.

1. `/student/editor/mid-review/topic`을 연다. 서버는 필요하면 최초 조회 시 중간보고서를 생성한다.
2. `주제 설명`의 원문을 기록한다. `E2E 자동 저장 검증 <실행시각>`으로 수정하고 입력칸 밖으로 포커스를 옮긴다.
3. 자동 저장이 끝나면 새로고침한다. 변경한 설명이 그대로 남아야 한다.
4. 원문으로 되돌리고 자동 저장이 끝난 뒤 학생 홈으로 이동한다.

**남는 데이터:** DRAFT 중간보고서와 저장 버전. 현재 자동 테스트에서는 중간보고서를 최종 제출하지 않는다.

## F07. 회의록 작성 → 액션 추가 → 수정 → 삭제

**계정:** L. **대응 코드:** `live/meetings.spec.ts`.

1. `회의록` → `새 회의록`으로 이동한다. 필수값이 비어 있을 때 `등록`이 비활성화돼야 한다.
2. 제목 `E2E 회의 <실행시각>`, 단계 `기획`, 날짜 실행일, 시간 `10:30`, 장소 `E2E 테스트실`을 입력한다.
3. 참석자 목록에서 한 명을 선택한다. 본문에 `E2E 회의록 본문. 역할과 진행 일정을 확인합니다.`를 입력하고 `등록`한다.
4. 상세 화면에서 같은 제목을 확인한다. `액션 추가`를 눌러 `<회의 제목> 구현 확인`을 입력하고 `추가`한다. 상세 화면에 액션이 보여야 한다.
5. `회의록 수정`에서 제목 끝에 `수정`을 붙여 저장한다. 새로고침 후 제목과 본문이 유지돼야 한다.
6. `회의록 삭제` → 확인 대화상자의 `삭제`를 누른다. 목록에 방금 만든 회의록이 없어야 한다.

다른 사람이 만든 회의록은 삭제하지 않는다. 자동 테스트는 생성 응답에서 받은 ID만 정리한다. 중간 실패 시 서버 담당자는 같은 ID의 액션·참석자 등 종속 데이터 정리 여부도 확인한다.

## F08. 상호평가 초안과 최종 제출

**계정:** 초안은 A, 최종 제출은 L. **시작 조건:** 열린 평가 폼, 각각 미제출 상태, 평가 대상 3명. **대응 코드:** `live/evaluation.spec.ts`.

1. A로 로그인하고 `/student/peer-review`를 연다. 초안을 이어서 열어 팀원 평가 단계가 보이면 `이전 설문`으로 돌아간다.
2. `자신의 역할 요약`: `E2E 기능 테스트와 API 검증`, `팀 프로젝트 평가`: `사용자 플로우를 함께 검증했습니다.`, `소감 또는 팀원 칭찬`: `팀원들이 역할을 나누어 검증했습니다.`를 입력한다.
3. `다음 설문`으로 이동한다. 표시된 팀원 3명의 `평가` 또는 `수정`을 순서대로 열어 기여도를 **34, 33, 33**으로 입력한다. 본인을 평가하지 않는다.
4. 각 대화상자에 기여 내용 `설계와 구현 내용을 검증했습니다.`, 한줄평가 `협업과 역할 수행이 좋았습니다.`를 입력하고 `평가 저장`을 누른다.
5. `합계 충족`과 활성화된 `제출하기`를 확인한다. **A는 제출하지 않는다.** 새로고침 후 합계와 제출 버튼 상태가 유지돼야 한다.
6. 로그아웃하고 L로 로그인한다. 동일한 입력 과정을 L의 평가 대상 3명에게 반복한다.
7. L은 `제출하기`를 누른다. 평가 화면을 다시 열면 `자신의 역할 요약` 입력이 비활성화돼야 한다.

**남는 데이터:** A는 DRAFT, L은 최종 제출 상태. A까지 제출하면 이후 기본 15개 중 초안 테스트를 반복할 수 없다. L의 제출을 초기화하지 않고 이 시나리오 전체를 다시 실행하면 실패하는 것이 정상이다.

## F09. 발표·최종보고서 파일 제출과 재제출

**계정:** L. **시작 조건:** 제출 기간 내, 각 마일스톤에 필수 PDF 항목 1개, 재제출 허용, 최종 완료 전. **대응 코드:** `live/submission.spec.ts`의 앞 2개, `@submit`.

1. 유효한 PDF 한 개를 준비한다. 파일명 예시는 `e2e-submission.pdf`, 크기는 5MB 이하다. 자동 테스트는 메모리에서 PDF를 생성하므로 별도 파일이 필요 없다.
2. 학생 홈의 `발표` 카드에서 `파일 제출` 또는 현재 상태에 표시된 재제출 버튼을 누른다. `발표 자료 제출` 대화상자가 열린다.
3. `제출 설명`에 `E2E 파일 제출 검증`을 입력한다. `변경 사항`이 표시되면 `E2E 재제출 검증`을 입력한다. PDF를 선택하고 `파일 제출` 또는 `파일 재제출`을 누른다.
4. `파일 제출을 저장했어요` 안내를 확인하고 닫는다. 새로고침 후 카드에 `제출 완료`가 표시돼야 한다. 첫 제출은 버전 1, 재제출은 이전 버전+1이다.
5. 홈의 `최종보고서` 카드에서도 반복한다. 대화상자는 `최종 파일 제출`, 기존 파일이 있으면 팀장 버튼은 `파일 교체`다.

**남는 데이터:** 제출 엔터티, 파일·산출물, 버전 이력. 최종보고서는 팀장이 새 버전에 자동 승인된 **1/4명** 상태가 된다. `제출 완료` 표시는 모든 팀원의 승인과 단계의 `최종 완료`를 의미하지 않는다. 재제출은 과거 버전을 삭제하는 초기화가 아니다.

## F10. 최종보고서 팀원 승인·취소

**계정:** A. **시작 조건:** F09 최종보고서 파일 존재, A 미승인, 단계 최종 완료 전. **대응 코드:** `live/submission.spec.ts`의 마지막 테스트, `@submit`.

1. A로 로그인하고 홈의 최종보고서 카드에서 `승인하기`를 누른다.
2. 버튼이 `승인 취소`로 바뀌어야 한다. 새로고침 후에도 승인 상태가 유지돼야 한다.
3. `승인 취소`를 누른다. 다시 `승인하기`가 표시돼야 한다.
4. L만 승인된 상태로 끝낸다. 자동 테스트는 도중에 실패해도 자신이 추가한 A의 승인을 취소하도록 정리한다.

## 3. 제출 포함 자동 실행

준비와 초기화가 끝난 baseline에서는 **“초기화된 계정으로 제출을 포함한 학생 실서버 E2E 20개를 검증해줘”**라고 요청한다. 아래 명령은 에이전트 내부 실행·문제 해결 참고다.

```sh
OOP_E2E_SUBMIT=1 pnpm test:e2e
```

일반 반복 검증은 **“OOP 학생 실서버 E2E 기본 15개를 검증해줘”**라고 요청한다(내부 실행: `pnpm test:e2e`). 기존 제출 이력을 유지하면서 파일 관련 3개까지 포함하려면 **“설문·상호평가 최종 제출을 제외한 학생 실서버 E2E 18개를 검증해줘”**라고 요청한다.

이 학생 18개 시나리오는 별도의 관리자·학생 통합 18단계와 다른 범위다. 다음은 내부 실행·문제 해결용 명령이다.

```sh
OOP_E2E_SUBMIT=1 pnpm --filter @aics/oop test:e2e:live --grep-invert '설문|상호평가 최종'
```

이 명령은 18개를 실행한다. 실행 직후에는 [전체 실행 후 기대 상태](../datasets/team2.after-full-run.json)와 비교하고 [초기화 체크리스트](./reset-and-seed.md#4-제출-후-초기화)를 사용한다. 현재 환경의 파일 버전은 과거 재실행 횟수만큼 높을 수 있다.

## 4. 현재 자동화 범위 밖의 최종 단계

제안서 최종 제출은 `e2e/proposal.spec.ts`의 독립 contract 테스트로만 검증했다. 중간보고서 최종 제출, 발표 평가, 모든 팀원 승인 후 최종 완료는 실서버 20개에 포함하지 않는다.

서버 담당자와 단계 종료까지 추가로 수동 확인하려면 기본 20개를 마친 뒤 별도 시나리오로 기록한다. 제안서·중간보고서는 각 작성 영역의 필수값과 완료 조건을 충족한 후 팀장으로 제출한다. 최종보고서는 A/B/C가 각자 로그인해 최신 버전을 승인하고, L이 `최종 완료`를 누른다. 완료 후에는 기본 테스트의 편집·재제출 조건이 달라지므로 다음 실행 전에 전체 초기화가 필요하다. 이 추가 단계의 성공 여부를 기존 20개 통과 결과에 합산하지 않는다.
